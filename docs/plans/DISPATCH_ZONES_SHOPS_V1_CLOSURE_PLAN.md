## 0. Tracking rules — how to close each item

- Stable identifiers `D00…D15` are the work ledger. `[ ]` = OPEN; `[x]` = merged, exact merged-main test evidence accepted; no optimistic ticks based on a worker handoff or an unmerged PR.
- **Only the LEAD** updates this plan, after checking the actual PR, final HEAD, current CI, Codex review, authorized test evidence and GitHub merge. Workers write their results in their own issues/PRs; no parallel edits to this file.
- Each completed item gets a short evidence note **under the item**, containing: `PR # / merged MAIN SHA / focused test names / PG16+Bearer result or explicit not applicable / CI / Codex / owner decision if needed`. If partial, leave `[ ]` and document partial evidence without disguising it as complete.
- Progress is tracked by these checkboxes; #831 holds the dashboard-level status and directs to the actual plan. One isolated responsibility per PR. Rebase on merged MAIN and merge/safely pull owner Windows `main` only after checks. No direct writes to `main`, local untracked files, backups, or user DB.
- Accepted product search/transport fixes and other historically merged improvements must not be repeated. Old sections 2–4 of `DISPATCH_V1_AUDIT_NOTES.md` are **superseded by §7 where noted**; any regressions require new evidence.
- V1 priority is **P0 security/stock/finance truth → P1 missing or dangerous required workflow → other functional gaps → narrowly necessary UX → final OWNER visual acceptance**. Real demonstrable first-company scale failures count; extreme scale without evidence is V2.

## 1. Architecture constitution — mandatory on every future PR

1. Follow `ARCHITECTURE.md` §§1–5, 12 and its mandatory decomposition discipline §§308–319 **exactly**; also `DRIVER_DISPATCH_MODULARIZATION_PLAN.md`, `DRIVER_DISPATCH_SEAM_INVENTORY.md`, `V1_SCOPE_FREEZE.md`, `.rules`, and `AGENTS.md`.
2. The system remains a single deployable modular monolith. No microservices, mass API renames, extra shared mutable authority, or a big-bang split during this page pass.
3. `wa_backend/api/dispatch.py` (~5,946 lines) and `wa_backend/api/driver.py` (~4,040 lines) are **shrinking legacy compatibility surfaces, NOT expansion points**. New business logic belongs under cohesive domain/application modules; if it depends on code trapped in a giant router, extract the **smallest cohesive existing seam** and preserve URLs, validation, transactions, locks, auth, response/retry and costing behavior. The touched legacy area must stay the same size or shrink in **business responsibility**. A new mega-file or god-function is forbidden. Do not physically split these large files now.
4. `dashboard/src/pages/DispatchBoard.tsx` (~2,085 lines) is likewise a shrinking composition shell, not the place for major new state/data/business logic. Build independently testable modules under `dashboard/src/features/dispatch/<responsibility>/`, reuse `dashboard/src/components/dispatch/` where appropriate, and keep read hooks, commands, contracts and presentation separate. No cosmetic broad rewrite.
5. Backend authority: canonical Backoffice capability + tenant + exact applicable location/route/vehicle; Field Representative is distinct. Inventory owns actual Warehouse/Vehicle custody, batch/FEFO/movements; Dispatch owns route/assignment/load orchestration; Pricing/Tax/Offers own publication/commercial rules; Finance/Costing owns financial value/COGS; no competing truth in UI or plan tables. A route status alone moves **zero stock**. Fail closed on permission revoke, ambiguous response or unknown custody.
6. Every PR must include an explicit file-ownership and module-boundary map. Cross-domain ownership decisions STOP and return to LEAD/owner; no agent may silently decide a new contract.

**Future target map (not a request to create all folders now):** `DRIVER_DISPATCH_MODULARIZATION_PLAN.md` §3 (thin `wa_backend/api/dispatch/{shop_zone,route_planning,route_inventory,route_lifecycle,settlement,shortages,read_models}` routers with application/domain ownership), `wa_backend/domains/dispatch/...`, and focused Dashboard dispatch feature modules. Preserve all existing public URLs during incremental extraction. No extra generic `shared.py`.

## 3. Stage 1 — business/contract decisions before dangerous mutations

- [ ] **D03 — Freeze essential decisions and exact scope contract.** Record the owner's decisions in #831 and this plan BEFORE dependent implementation:
  1. **Shop financial edit:** ordinary changes of name/phone/zone/details MUST NOT silently change receivables; determine legitimate opening-balance/authorized manual adjustment process and Finance-owned immutable audit. Preserve useful initial-balance onboarding without conflating it with current balance. Do not silently remove a required financial action or create a second finance ledger.
  2. **Shortages group:** UI shows group edit and Delete All; choose an **atomic authorized group replace/delete with stable replay/recovery** or expressly remove/defer those controls from V1. Do not simulate atomicity by multiple client DELETE requests. Default proposal: implement the promised atomic server command behind a new focused module/compatible endpoint.
  3. **Dispatch reads:** determine who can view *company-wide Shops, financial balances, Zones and representative names* when the Backoffice principal has `dispatch.read` for only **one** Warehouse. `/dispatch/active_routes` already scopes routes, while `/dispatch/init` and `/dispatch/shops` return broader company data. Confidentiality policy must be explicit and enforceable at backend; do not assume a company grant automatically permits all finance/client data.
  4. **Route launch retry:** determine stable `request_id`/equivalent command replay and recovery expected when successful 201 response is lost, while preserving route uniqueness and immutable published commercial context; promote to P1 if test proves first-company recovery gap.
  5. **Route “cancel”, closed history and explicit “unschedule”:** no dedicated cancel/history router was found; existing route `status=closed/postponed/waiting` and its UI do not automatically require new endpoints. Only add a V1 feature if owner workflow truly needs it; otherwise record the intentional V1 boundary.
