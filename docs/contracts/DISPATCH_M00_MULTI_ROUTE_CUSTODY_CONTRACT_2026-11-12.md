## 2. Frozen target identity and state machine (proposal for M01; no runtime table yet)

- **Route identity**: the territory/zone task with durable shops, completed visits, target date and historical progress. One route may have several execution periods, on one or multiple days. A postponed route alone still reserves its zone; a closed route releases its zone for a separately numbered future route. Completed visit identities stay immutable.
- **WorkSession identity**: one representative's operational/financial work-day (S1), not a route. Only one open session per representative; S1 may span R1/A → R2/B → R1/A, with no interim forced settlement. Next day requires closed/financially settled S1 before separate S2. A session's commercial context is **not** shared as the single context for multiple route price publications.
- **Execution period** (candidate table `dispatch_route_execution_periods`): `id, company_id, route_id, work_session_id nullable during pre-start assignment, driver_id (bounded compatibility only), field_representative_id (canonical authority), vehicle_id, vehicle_location_id, started_at, ended_at, state, context_revision, commercial_context_id, started_by, ended_by, reason, request_id`. Composite same-company FKs; forbid start without correct company, route, vehicle custody authority and live session. Every executed Visit/invoice/collection carries persistent period + original session + actual physical vehicle-location identity. Never rederive old vehicle from current route assignment.
- **Vehicle responsibility epoch** (candidate table `vehicle_custody_epochs`): `id, company_id, vehicle_id, inventory_location_id, custodian_kind, custodian_principal_id/representative_id, related_session_id nullable, start_at, end_at, accepted_by, handoff_reference, context_revision`. Handoffs change *responsibility* and require explicit acceptance even with zero quantity; they do not change `InventoryBalance`. Custody with no active route is valid if an authorized party remains responsible. Do not treat legacy Driver IDs as authorization.
- **Uniqueness**: zone protection remains for active/waiting/postponed routes; only one currently open live execution assignment per driver and per vehicle (`ended_at IS NULL`, operational `active/waiting`). One current custody epoch per vehicle/location, guarded tenant FKs and sorted locks. A postponed route has no open/live **assignment** period, regardless of preserved last driver/vehicle history. Only one open S1 per field representative. Backend 409 remains for real collision; none of these rely solely on client filtering.
- **Fencing**: every assignment, custody handoff and period transition increments monotonically a context/epoch revision. An old request from A cannot succeed in B nor on ABA A→B→A (same visible car but a *new* revision). Same `request_id` and exact request hash permit idempotent lost-response replay; reused ID with different payload fails closed.
- **Transactions**: protect principal/representative, current session, route/zone, vehicle + custody epoch, physical location (if actual movement) in one documented deadlock-safe lock order. Never hide a stock movement in a status change; Finance/Inventory changes use their owning domain application services.

## 3. Versioned command/API contract freeze — initial shapes (NOT existing endpoints)

Keep existing `/dispatch/*`, `/driver/*`, `/admin/sessions/*` URLs during expand/contract. Only add bounded contract endpoints/fields where genuinely needed; do not assume below is already supported. Stable codes + `context` + `request_id`; 401/403 unauthorized, 409 conflict/stale/ABA, 422 malformed or inconsistent evidence.

| Command/read | Minimum authoritative contract | On success / rejection |
| --- | --- | --- |
| Availability for launch/resume | Authorized zone/driver/vehicle state; available-first ordered entries; reason visible only with capability; current period/custody revision | Backend revalidates under lock at mutation. Postponed alone does not busy driver or vehicle; custody/other live assignment still may. |
| Postpone route | route ID, previous revision, stable request ID, requested action | End live execution period; retain route/visits and zone lock; clear live assignment. No stock move. Preserve explicit vehicle custodian. |
| Resume / switch assignment | route ID, target representative AND vehicle, expected route/epoch revision, stable request ID | Verify live session/availability, accept required custody handoff, create fresh period with commercial snapshot. Reject unauthorized, unsettled, stale or already assigned. |
| Close / schedule another | route ID, expected revision, stable request ID | Close period/zone reservation; next schedule creates **new** route identity, never changes historic visits. |
| FIELD active context | current `session_id`, `route_id`, `period_id`, `vehicle_id`, `vehicle_location_id`, `context_revision`, capability/scope-scoped authorized reads | Client atomically rebinds view; stale saved A mutations are quarantined/reconciled under old exact context, never silently switched to B. |
| End day / vehicle read | session and every distinct custody epoch and vehicle inventory snapshot | End S1 without artificial stock movement; preserve outstanding custody even after route closed. |
| Count in place | session, vehicle location, signed receiver/custodian, exact product/real lot/status quantities, snapshot/epoch revision, request ID; **no warehouse destination** | Seal matching count and custody acceptance; no movement. Variance becomes `VEHICLE_RECON` pending correct review. Only approved difference changes same Vehicle location. |
| Physical handoff | existing receiver-confirmed Warehouse destination + counted items + request ID | Preserve real Vehicle→Warehouse movements, stock status, lot and audit exactly; cannot masquerade as in-place count. |
| Financial settle | session, every vehicle's accepted sealed checkpoint, actual cash/reasons, stable request ID | Aggregate immutable S1 events once; block pending counts/handshakes/variance/epoch changes. Closing S1 allows new S2 counters without changing Vehicle balances. |

**Backward compatibility:** legacy route's `work_session_id`, session commercial context and existing receipts remain readable during transition, not mutable truth for multi-period operations. Once new period model is active, old FIELD/UI mutation requests missing a required current period/epoch must fail closed rather than inherit a newly assigned vehicle. Status-only legacy commands that require no new context may retain previous results where safe.

4. Dual-read parity against existing approved single-route scenarios; migrate each writer **transactionally** behind one canonical API. 6. **Rollback:** additive schema and old reader compatibility allow rollback **before** new multi-period writes; after first new multi-route/epoch write, code rollback must fail closed or use forward-only remediation. Never simply drop data/period history or re-enable one-to-one routing as if it were valid. A destructive downgrade requires approved data repair/backup and documented impact.
