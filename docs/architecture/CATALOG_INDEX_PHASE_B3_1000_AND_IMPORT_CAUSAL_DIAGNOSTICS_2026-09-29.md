## 2. Reproducible 1,000-product CORE execution profile

Ran the unmodified `simple_products.create_products_and_prices` authority with **10 × 100** independent, committed batches of newly generated unique test products, one real SKU per parent, EACH+CARTON (24 base units), two sale-price entries per SKU, standard tracking NONE, and one actual price publication per 100 products. Used the same source module, live tenant RLS and schema constraints; a bounded SQLAlchemy execution listener counts actual statements/SQL time. **This is the CATALOG STRUCTURE + PRICING CORE, NOT a complete XLSX or CSV import, not a real Procrastinate queue, and not a clone of the 217k-row catalog.** No barcode, multi-company contention, user uploads, full staging/validation or active customer price books were included.

| Scenario in an isolated small clone | 1,000 product/SKUs | SQL statements | SELECTs | Wall duration | Physical catalog index growth |
|---|---:|---:|---:|---:|---:|
| Full original indexes, no UOM cache (first run) | 1,000 | **20,273** | 10,201 | **29.927 s** | **3,244,032 bytes** |
| Remove only the TWO non-unique trigram GIN indexes inside a disposable comparison clone | 1,000 | 20,273 | 10,201 | **27.534 s** | **589,824 bytes** |
| All original indexes, UOM cache (separate run under different host load) | 1,000 | 18,293 | 8,221 | **39.441 s** | 3,227,648 bytes |
| Paired same-host, freshly reset identical disposable clone **uncached** | 1,000 | **20,273** | 10,201 | **36.474 s** | 3,252,224 bytes |
| Paired same-host, freshly reset identical disposable clone **cached** | 1,000 | **18,293** | 8,221 | **31.895 s** | 2,916,352 bytes |

**Interpretation:** 20.273 SQL calls per product, with **7,013 INSERTs**, **3,039 UPDATEs**, **10,201 SELECTs** and **20 WITH** per 1k original run, is directly observed **per-row SQL/write amplification in the core creation/pricing path**, NOT evidence that every full import row has exactly 20 statements. The paired batch-local UOM reuse removes exactly **1,980 SQL calls per 1,000 products** (~9.8% fewer SQL commands) without changing created counts, pricing or transaction structure; a paired run was **4.579 seconds faster** (~12.6% of its uncached baseline). The separately observed **39.441 s** slower cached run is preserved above: host/background effects make one timing an insufficient release-level p95 result. Treat only the SELECT-count reduction and passing functional tests as deterministic; collect repeated randomized A/B and production-size data before promising speed percentages.

**GIN A/B caution:** removing two search indexes makes the *isolated index bytes* much smaller; it changes end-user search behavior and is **NOT** an approved production change. The 2.393-second difference across separate, non-randomized runs does **not** establish that GIN is the major cause of the 45.76-minute real job. Real tenant-38 EXPLAIN showed index-only scans for default product/SKU and active sort lists (0.152 ms, 0.038 ms and 0.09 ms in the specific probes), while a sample composite-trigram text query cost **92.659 ms** and read **3,153 shared hit blocks** with a large company-scoped bitmap. Investigate the **actual application search SQL** before changing its index or declaring it redundant. Exact SKU equality used the `uq_company_sku` UNIQUE index.

## 3. Physical page-level findings (pgstattuple ON CLONE ONLY)

The original 18 catalog indexes were measured with `pgstatindex` for B-tree and `pgstatginindex` for GIN at T0, after 100 and after 1,000 additions.

- In the initial full-index 1k experiment, GIN growth was **2,048,000 bytes** for `ix_product_variants_company_search_trgm` and **581,632 bytes** for `ix_products_company_name_trgm`. Together **2,629,632 bytes of 3,244,032** catalog index growth (~81%); these pages include normal GIN pending-list growth and **cannot be labeled all bloat**.
- At 1k, the variant GIN pending list had **251 pending pages / 2,001 pending tuples**; Product-parent GIN had **72 pending pages / 1,001 pending tuples**. These are *direct measurement of the early pending-list burst*, not proof that the pending entries survive autovacuum, waste storage after consolidation, or slow every search.
- The fresh-clone B-tree `pgstatindex` measures showed **0 deleted and 0 empty pages** after this insert-only microbenchmark. Examples: `ix_product_variant_company_name_id` leaf density **82.82%**, `ix_product_variant_live_active_seek` **80.40%**, and `uq_company_sku` **57.27%** (26.67% reported leaf fragmentation). Insertion order/random SKU key distribution merits later growth/churn testing; zero deleted pages in a fresh clone says nothing about deleted pages in the older live catalog.
- Crucially, a normal product creation produces one `ProductVariant` INSERT in `DRAFT` followed by its authorized `ACTIVE` publish UPDATE. After 1,000 products the clone measured **1,000 variant INSERTs, 1,000 variant UPDATEs, ZERO HOT updates, 1,000 estimated dead tuples**. Changes to indexed lifecycle columns require fresh index entries and are a directly observed *normal-life-cycle source of per-new-SKU write churn*. **Do not skip DRAFT→ACTIVE or delete the active index** without separately approved lifecycle/permissions/event semantics.
- The source developer DB global post-REINDEX catalog baseline was **4,964,352** Product-parent index bytes and **72,187,904** variant index bytes, with historic **996,750 inserts / 476,879 deletes** and **2,395,689 inserts / 1,786,141 deletes** respectively. Earlier manual REINDEX recovered substantial physical space. This supports a strong **historical churn / index-page-reuse hypothesis** (especially given repeated 50k-row test imports), **but does not prove the exact bloat percentage or rate on the active database**. Source statistics are global/lifetime, whereas the detailed pgstattuple samples above are from brand-new one-tenant clones.

## 4. Confirmed engineering code issue and narrow tested repair

- The original `wa_backend/domains/simple_products/service.py` `create_product_structures` called `_load_shape_for_spec` once for each row, which queried global UOM codes `EACH` + `CARTON` again and again. The fix adds an **entirely batch-local, short-lived** map of `UOM.code → UOM` for that single transaction; normalized code and missing-reference failures are unchanged; no cross-tenant/session/global memory cache exists.
- Tests: `wa_backend/tests/test_catalog_batch_uom_cache_b3.py` **6/6 PASS** for batch reuse, distinct UOM codes, no package, independent sessions, fail-closed missing UOM and original noncached API behavior. Product Import **145/145 PASS** as part of this checkpoint. Full C1/C2/sale/cost/import+family combined regression and Stage74 gate are recorded separately in the urgent plan. This change is a technical query deduplication and does not alter price/cost formulas, SKU identities, RLS, idempotency or UOM conversions.

## 5. Treatment path — do not confuse symptoms with a fix

1. **Next core performance work (OPEN):** instrument source-level `_resolve_family` (one advisory lock/name lookup per legacy product), `_load_shape_for_spec`, repeated product-tracking default resolves, and `domains.pricing.publishing.create_draft_entry` (one draft publication `FOR UPDATE`, variant/UOM validation and flush per **price entry**). The verified two-entry-per-SKU publication loop and repeated SQL suggest a *version-safe bulk pricing application API* within the Pricing domain. Preserve publication versions, maker/checker, effective dates, historical prices, book/tenant/RLS authority, domain events, request idempotency and rollback before changing the implementation. **Do not bypass pricing validation or lump unrelated tenants together.**
2. **Persistent bloat remediation (OPEN):** measure **real page density on a representative disposable catalog containing the previous live data volume or equally characterized synthetic data**; controlled same-semantic 5k, 10k, 50k import/retire/delete cycles; subsequent ordinary VACUUM/autovacuum cycles; examine B-tree page splits, reuse/free pages and GIN pending-list flushing. Compare each index's byte growth against *net live SKUs*, not only inserted SKU count. Do not assume index bytes proportional to row count; deleted B-tree pages often remain allocated for reuse rather than shrinking.
3. **Autovacuum (OPEN):** variant base scale-factor `0.2` means an estimated trigger near **43,461 dead tuples** at global estimated 217,055 rows. One non-HOT indexed lifecycle UPDATE for each inserted SKU plus repeated test-data deletion means this threshold could be reached in bursts. Derive a per-table threshold/scale factor from measured throughput and disk/headroom, and test a bounded stronger policy on a disposable clone; do not copy import-row settings blindly or issue `VACUUM FULL` as normal operation.
4. **Search and hot-query plans (OPEN):** preserve UNIQUE, PK and composite tenant FK indexes even with read scan=0. Evaluate overlapping active/list name B-trees only after **actual application** `EXPLAIN (ANALYZE, BUFFERS)` over representative RLS tenant catalogs; the active and generic name indexes were **both used** by separate real sample queries. Verify query semantics/latency and write cost before any candidate `DROP INDEX CONCURRENTLY` migration, with rollback.
5. **50k elapsed-time explanation (OPEN):** add bounded per-stage timing of source acquisition/Excel parsing, validation/staging, job queue wait, SQL statements by family/variant/pricing and each 100-row transaction; compare identical 1k/5k/10k/50k real import distributions. The measured small-database service microbenchmark cannot explain all 45.76 minutes. Also isolate monitor saturation/worker queues (Phase C) from file import work. Do not enlarge worker concurrency until it is measured.

**No production schema changes or live `CREATE EXTENSION`, `REINDEX`, `VACUUM`, `DROP INDEX`, worker restart, main-branch merge or user-file cleanup were made by B3.** All disposable benchmark fixtures were destroyed after their PG16 instance stopped, and the source synthetic company 2 was verified unchanged.
