## 1. End-to-End Data Lifecycle

This section traces, step by step, how data physically moves through the four layers (Flutter / React clients → FastAPI routers → SQLAlchemy/PostgreSQL → back to clients) for the five most critical business flows in the system.

### (A) Auth — Driver & Admin Login

1. **Flutter (driver login)** — `login_screen.dart` collects `username`/`password` and dispatches `LoginRequested` to `AuthBloc` (`blocs/auth/auth_bloc.dart`).
2. `AuthBloc._onLogin` calls `ApiClient.instance.post('/driver/login', data: {...})`. The Dio singleton (`core/network/api_client.dart`) attaches JSON headers; `AuthInterceptor.onRequest` tries to inject a bearer token from `flutter_secure_storage`, but at this stage no token exists yet, so the request goes out unauthenticated.
3. **FastAPI (`api/auth.py::driver_login`)** — receives the payload validated against `LoginRequest` (Pydantic: `username` min_length 2, `password` min_length 4). It calls `get_real_ip()` and `check_brute_force()` (reads `SystemAuditLog` for `FAILED_LOGIN` rows in the last 15 minutes, raises 429 if ≥ 5). It queries `Driver` by `username`+`is_active` via SQLAlchemy `select()`, computes a bcrypt check (via `asyncio.to_thread` to avoid blocking the event loop) against either the real hash or a `DUMMY_PASSWORD_HASH` (timing-attack shield when the user doesn't exist).
4. On success, `create_access_token()` builds a JWT (`HS256`, 24h expiry) carrying `sub` (driver id), `is_admin`, `username`, signed with `Config.SECRET_KEY`. The response is validated against `LoginResponse` and serialized to JSON: `{message, token, driver_id, driver_name, is_admin}`.
5. **Flutter** — `AuthBloc` receives the Dio response, casts `response.data` to `Map<String,dynamic>` defensively, extracts `token`/`driver_id`, and persists both into `flutter_secure_storage` (`auth_token`, `driver_id`). It emits `AuthAuthenticated(driverId)`.
6. From this point on, **every** subsequent Flutter HTTP call passes through `AuthInterceptor.onRequest`, which reads `auth_token` from secure storage and injects `Authorization: Bearer <token>` — this is the sole trust boundary for the mobile client into FastAPI.
7. **React (admin login)** — `pages/Login.tsx` calls the backend directly via raw `fetch` (not through `useAuthFetch`) against a **hardcoded** `http://127.0.0.1:5000/login` URL, which hits `api/auth.py::admin_login`. Same brute-force/timing-attack logic runs server-side, plus an extra check: `if not admin.is_admin: raise 403`. On success, the token is stored in `localStorage` (`admin_token`).
8. Every subsequent React request goes through `useAuthFetch()` (`dashboard/src/hooks/useAuthFetch.ts`), which reads `admin_token`/`token` from `localStorage`, prefixes `VITE_API_URL`, injects the bearer header, parses JSON, and on `401` clears storage and redirects to `/login`.
9. **PostgreSQL involvement**: Auth reads/writes only the `drivers` table (credential lookup) and `system_audit_logs` (brute-force counters, `FAILED_LOGIN` entries) — no other domain tables are touched during login.

### (B) Dispatch & Handshake (Morning Load + Mid-day Transfer)

**Morning dispatch (`POST /dispatch/route`, `api/dispatch.py::dispatch_route`)**
1. React `DispatchBoard.tsx` collects `zone_id`, `driver_id`, `vehicle_id`, and a per-product cartons map (`inventory: {variantId: cartons}`) from the launch form, then calls `authenticatedFetch('/dispatch/route', {method:'POST', body: JSON.stringify(payload)})`.
2. FastAPI validates the payload against `DispatchRouteRequest`, checks the warehouse lock flag (`SystemSetting.warehouse_status`), locks the target `Driver` row (`with_for_update`), and verifies no conflicting active/waiting route already exists for that zone/driver/vehicle.
3. A new `DispatchRoute` row (`status='active'`) is created. If the driver has **no active `WorkSession`** yet (morning case), the endpoint locks `VehicleLoad` rows for that vehicle, locks `MainWarehouse` rows for every involved `product_variant_id` (sorted ascending to avoid deadlocks), computes `delta_packs` between requested and currently-loaded quantities, deducts/returns `MainWarehouse.available_quantity_packs`, upserts `VehicleLoad`, and writes an immutable `WarehouseLedger` entry (`DISPATCH_LOAD`/`DISPATCH_UNLOAD`).
4. The same endpoint also "adopts" orphan `Visit` rows in that zone (`driver_id IS NULL`) and creates fresh `Pending` `Visit` rows for any shop not yet visited today, tagging shops with open `ShortageRequest`s as `is_emergency=True`.
5. **Driver starts the day** — Flutter `dashboard_screen.dart` calls `POST /driver/{id}/sessions/start` (`api/driver.py::start_work_session`). The backend locks the `Driver` row, verifies an `active` `DispatchRoute` exists, creates the `WorkSession`, links `active_route.work_session_id = new_session.id`, and — this is the literal "handshake" — copies every `VehicleLoad` row into a fresh `SessionInventory` row per product (`starting_quantity = load.quantity * packs_per_carton`). A bulk `UPDATE visits SET work_session_id=...` binds all pending zone/emergency visits to this new session.
6. **Mid-day handshake** (driver already has an active `WorkSession`) — the *same* `dispatch_route`-adjacent code path (`adjust_route_inventory` / the `else` branch inside `dispatch_route`) instead creates `InventoryTransfer` rows with `status='pending'` and moves the requested packs from `MainWarehouse.available_quantity_packs` into `MainWarehouse.reserved_quantity_packs` (an "in-transit" holding state), writing a `HANDSHAKE_RESERVE` ledger entry. **Nothing is added to the driver's live `SessionInventory` yet.**
7. **Driver-side acceptance** — Flutter `DashboardBloc` polls `GET /driver/transfers/pending` (triggered after `FetchDashboardData` if a session is active) and shows a dialog; the driver responds via `PUT /driver/transfers/{id}/respond` (single) or `PUT /driver/transfers/batch_respond` (batch, up to 100). Only **now** does the backend (`respond_to_transfer` / `batch_respond_to_transfers`) lock `VehicleLoad` → `MainWarehouse` → `SessionInventory` (in that fixed lock order to avoid cross-module deadlocks), move `reserved_quantity_packs` back down, update `VehicleLoad.quantity`, and finally increment `SessionInventory.current_remaining_quantity` + `net_transfers`. A `HANDSHAKE_COMMIT` (or `HANDSHAKE_RELEASE` on rejection) `WarehouseLedger` row and an `InventoryLedger` row are written.
8. **React visibility loop** — `DispatchBoard.tsx` polls `/dispatch/active_routes` and `/dispatch/shortages` every 60 seconds (`setInterval`) to reflect the transfer's eventual acceptance/rejection, and `TransfersRadarModal.tsx` fetches `/dispatch/route/{id}/transfers` on-demand to show per-transfer status (`pending`/`accepted`/`rejected`).

### (C) Offline Field Visits (Sale/NoSale/Postponed)

1. Flutter `visit_screen.dart` builds a `CartItemModel` list in `VisitBloc` (`AddOrUpdateCartItem`, `RemoveCartItem`, `UpdateCashCollected`, `UpdateDebtPaid`), computing `totalSales`, `netInvoice`, and `expectedNewBalance` purely client-side against data cached from the last `syncDown()`.
2. On submit, `VisitBloc._onSubmitVisit` assembles a payload (`cart_items`, `returns`, `outcome`, `cash_collected`, `debt_paid`, `notes`) and calls `SyncRepository.saveInvoice(visitId, payload)`.
3. `SyncRepository.saveInvoice()` **always** attempts the network call first (`_dispatchPendingRecord(type:'submit_sale', ...)` → `PUT /visits/{id}`). If it succeeds, the local SQLite `visits` row is updated immediately (`updateVisitStatus`) and local vehicle stock is decremented (`deductInventoryLocal`) so the driver's dashboard reflects the sale instantly — no server round trip is needed to see updated stock.
4. **If the network call fails** (Dio error with no HTTP response, i.e. truly offline, or a 5xx) the repository: (a) calls `revertOfflineVisit(visitId)` to undo any *previous* offline draft for the same visit (preventing double-deduction), (b) persists the full payload into the `pending_sync` SQLite table via `addPendingSync(type:'submit_sale', payload: json)`, (c) still calls `updateVisitStatus` and `deductInventoryLocal` so the UI stays consistent offline. If the server responds with a genuine 4xx (business rejection, e.g. debt ceiling exceeded), the exception is **rethrown** and NOT queued — the driver must fix and resubmit.
5. **Server-side processing** (`api/driver.py::update_visit`, when online) is the single largest transactional unit in the codebase: it row-locks the `Visit`, checks session settlement/ownership/zone/authorization/break/pending-transfer guards, calls `services.reverse_previous_visit_state()` if the visit was previously `Completed` (to safely re-process an edited visit), computes per-item invoices via `services.calculate_invoice()` (pure function, requires pre-fetched tax % and active `OfferRule`s), locks and mutates `SessionInventory` rows, writes `VisitItem`/`VisitReturn`/`InventoryLedger` rows, applies debt-ceiling checks (`services.check_debt_limits`), updates `Shop.current_balance`, and finally commits — returning `{"message": ..., "new_balance": "..."}`.
6. Back in `SyncRepository._dispatchPendingRecord`, on success the returned `new_balance` is written directly into the local `visits.shop_balance` column via a raw `UPDATE` — this is the only place the server's authoritative financial state is reflected back into SQLite outside of a full `syncDown()`.
7. **Reconnect flow** — whenever `syncDown()` runs (dashboard fetch, manual refresh, or new session start) it first calls `syncUp()`, which iterates every `pending_sync` row FIFO (`created_at ASC`), replays it against the same `PUT /visits/{id}` endpoint, deletes the row on success, keeps it queued on business-rule 4xx, and stops the whole loop on auth errors (401/403) or connectivity/5xx errors to avoid data loss.
8. Once all blocking pending items are cleared (or only harmless `submit_sale` remain), `syncDown()` proceeds to call `GET /driver/{id}/visits`, parses the response off the main isolate (`compute(_parseVisits, ...)`, `compute(_parseProducts, ...)`), and calls `LocalDatabase.refreshSessionData()` which wipes and rewrites `products`+`visits` inside a single SQLite transaction — the server's view of the world now fully overwrites the local cache (except still-pending offline items).

### (D) Settlements (End-of-Day Financial Close)

1. Flutter driver ends the day: `PUT /driver/{id}/sessions/end` — guarded against active breaks and pending inventory transfers; simply stamps `WorkSession.end_time`.
2. React `OperationsDashboard.tsx` polls `GET /admin/sessions/today` every 10 seconds (`setTimeout`-based recursive poll) to see the session move into `"مغلقة بانتظار التسوية"` status, aggregating cash/visit/inventory stats server-side via SQL conditional aggregation (`func.sum(case(...))`) to avoid N+1.
3. Admin opens `SettlementModal.tsx`, which is pre-seeded from the `driver.settlement` object already embedded in the `/admin/sessions/today` response (or `GET /admin/sessions/{id}/settlement_report` for a focused view), letting the admin edit the physical stock count (`actual_cartons`/`actual_loose_packs`) per product and the actual cash counted.
4. Confirmation calls `PUT /admin/sessions/{id}/settle` (`api/dispatch.py::settle_session`) — a large transactional block that: locks the `WorkSession`, computes `expected_cash` vs `actual_cash` (writes `SystemAuditLog` if they differ), locks `SessionInventory` for the whole session, deletes the vehicle's *entire* `VehicleLoad` rowset (to rebuild it fresh from the settlement), locks `MainWarehouse` for every involved product, reconciles declared `DamagedItemLog` entries from unsettled `VisitReturn`s, computes `expected_total_physical = sellable + damaged`, compares against the admin-entered `actual_qty`, records `Surplus`/`Deficit` `InventoryLedger` entries plus `SystemAuditLog` (`INVENTORY_DISCREPANCY`) when they differ, and requires a non-empty `notes` field if there is ANY cash or inventory discrepancy (hard business rule, enforced with an `HTTPException(400)` if violated).
5. Remaining sellable stock is split: loose packs return to `MainWarehouse.available_quantity_packs` (`DISPATCH_UNLOAD` ledger entry), whole cartons stay in the vehicle as a fresh `VehicleLoad` row for tomorrow (`VEHICLE_ROLLOVER` ledger entry) — or, if there's no route/vehicle association, everything is force-returned to the warehouse (`DISPATCH_UNLOAD_FALLBACK`).
6. `WorkSession.is_settled = True` is set, and the route's `work_session_id` is cleared, fully decoupling the settled session from any future dispatch. The endpoint returns `{"cash_difference": "...", "is_settled": true}`, which the React modal uses to show a success toast and re-triggers `fetchLiveOperations()` to refresh the board.
7. **Data never flows back to Flutter for a settled session** — once `is_settled=True`, `update_visit` explicitly rejects any further edits to visits under that session (`403` guard), so the settlement is a one-way, backend-and-dashboard-only terminal state as far as the mobile client is concerned.

### (E) Warehouse Inbound (Supplier Receiving)

1. React `Tab2Inbound.tsx` (under `pages/inventory/MainInventory.tsx`) builds a list of `{product_variant_id, quantity_packs}` rows (converted from cartons+loose via `toTotalPacks()`), requires a non-empty `reference_id` (supplier invoice number), and calls `authenticatedFetch('/warehouse/inbound', {method:'POST', body: {...}})`.
2. `api/warehouse.py::warehouse_inbound` checks the global `warehouse_status` lock (`AUDIT_LOCK` blocks all inbound), rejects duplicate `reference_id`s (case/whitespace-insensitive match against prior `INBOUND_SUPPLIER`/`INBOUND_CORRECTION` ledger rows) to prevent double-booking a supplier invoice, aggregates duplicate line items in the payload itself, validates every `product_variant_id` exists, locks `MainWarehouse` rows (sorted by id), increments `available_quantity_packs`, and writes one `WarehouseLedger` row per product with a `balance_after_packs` snapshot for auditability.
3. On success, the response `{"message": ...}` triggers `onSuccess()` in the React tab, which re-fetches `/warehouse/inventory` and `/warehouse/ledger` to refresh `Tab1LiveStock` and `Tab4Ledger` — there is no push notification; the dashboard's other tabs only refresh because the user is redirected/the parent component re-fetches on tab switch or manual action, not via a live subscription.
4. This new warehouse balance becomes immediately available to the **next** dispatch/handshake operation described in (B) — i.e., Warehouse Inbound → Dispatch → Session Inventory → Visit is the full physical-to-financial pipeline of one unit of stock.

## 2. Request/Response Serialization

- **Backend contract layer (`wa_backend/schemas.py`)** is the single, authoritative serialization boundary. Every FastAPI route declares a Pydantic `response_model` and/or request body model; incoming JSON is parsed and validated by Pydantic *before* any route handler code runs, and outgoing ORM objects (`from_attributes=True` configs) are serialized back to JSON by Pydantic on the way out — SQLAlchemy model instances are frequently returned directly from route handlers (e.g., `return visit` in `get_visit_details`) and Pydantic performs the object→JSON projection.
- **Financial/decimal safety**: nearly every money or heavy-integer field uses a `BeforeValidator` (`clean_finance_str`, `clean_null_price`, `safe_decimal_input`, `clean_zero_packs`) to coerce `None`/empty-string/malformed inputs into safe defaults (e.g., `"0.000"`) and to force monetary values to be serialized as **strings**, not floats — this is a deliberate mechanism to prevent floating-point precision loss for currency across the JSON boundary to both React and Flutter.
- **Flutter request serialization**: `SyncRepository`/`VisitBloc` build plain `Map<String, dynamic>` payloads by hand (not typed DTOs) and pass them to Dio, which JSON-encodes them automatically; `jsonDecode(jsonEncode(payload))` is used defensively in `saveInvoice()` purely to obtain a deep, safely-serializable copy before further mutation.
- **Flutter response deserialization**: all incoming JSON is funneled through hand-written `fromJson` factory constructors (`VisitModel.fromJson`, `ProductModel.fromJson`) that use `int.tryParse`/`double.tryParse` against `.toString()` of every field — a defensive pattern that tolerates the backend sending numbers as either native JSON numbers or strings (the latter being common for the Decimal-as-string fields described above) without crashing the app.
- **Flutter local persistence serialization**: `VisitModel.toJson()`/`ProductModel.toJson()` produce SQLite-compatible flat maps (nested `cart_items`/`returns` are stored as JSON-encoded **text columns**, not relational rows) — SQLite here acts as a simple flattened key-value/document cache rather than a normalized relational mirror of the backend schema.
- **React request/response serialization**: `useAuthFetch()` performs raw `fetch()` + `JSON.stringify()`/`res.text()` → `JSON.parse()` manually; there is no shared TypeScript response-typing layer analogous to Pydantic — components consume `any`-typed JSON directly (e.g., `data.map((d: any) => ...)` in `OperationsDashboard.tsx`), meaning the React side has no compile-time contract validation against the backend schema, unlike the Flutter side's `fromJson` factories or the backend's Pydantic models.
- **Dual serialization inconsistency**: because the backend deliberately emits monetary fields as strings, both clients must re-parse them (`double.tryParse` in Flutter, `parseFloat`/implicit numeric coercion in React) — this pattern is consistent but is manually repeated in many call sites on both client codebases rather than centralized in one parsing utility per client.

## 3. Offline-First Synchronization Flow (Flutter ↔ SQLite ↔ Backend)

The offline engine is entirely concentrated in `SyncRepository` (`repositories/sync_repository.dart`) sitting between `LocalDatabase` (SQLite) and `ApiClient` (Dio/HTTP), as identified architecturally in `01_ARCHITECTURE.md`. Its three operations form a closed loop:

1. **`syncUp()`** — drains the `pending_sync` SQLite table FIFO (`ORDER BY created_at ASC`). For each row it decodes the stored JSON `payload`, dispatches it to the correct endpoint via `_dispatchPendingRecord()` (currently supports `submit_sale` → `PUT /visits/{id}`, and `toggle_break` → `PUT /driver/{id}/sessions/break`), and on HTTP success deletes the row (`deletePendingSync`). Error handling is tiered:
   - 4xx **401/403** → the whole loop `break`s immediately (auth is broken; don't burn through the queue against a rejected token, preserve everything for the next attempt after re-login).
   - Other 4xx (business rule rejection, e.g. debt ceiling) → `continue` (skip this record only, leave it queued for manual correction by the driver).
   - No response / 5xx (real connectivity or server outage) → `break` (stop entirely, retry later).
   - Any other unexpected exception → `continue` (treated as a "poison pill" — skipped rather than freezing the whole queue).
   - A boolean lock (`_isSyncing`) prevents concurrent invocations of `syncUp()` from racing each other.

2. **`syncDown()`** — first internally calls `syncUp()` (best-effort flush of anything already queued), then applies a **hard block**: if any pending record exists whose `type` is *not* `submit_sale` (i.e., something more structurally sensitive), it throws and aborts the whole sync — this protects against overwriting local state that the server hasn't yet acknowledged for non-sale operations. If the guard passes, it reads the driver id from secure storage, calls `GET /driver/{id}/visits`, defensively parses either a raw list or a `{visits, inventory}` object shape, offloads JSON→model parsing to a background isolate via `compute()` (`_parseVisits`/`_parseProducts` top-level functions) to avoid jank on large payloads, and finally calls `LocalDatabase.refreshSessionData()` — a single SQLite `transaction()` that deletes and re-inserts both `products` and `visits` tables atomically, guaranteeing no partial/torn state if the app is killed mid-sync. A separate boolean lock (`_isSyncingDown`) prevents concurrent `syncDown()` calls.

3. **`saveInvoice()`** — the "write path" companion described in detail in section 1(C): attempt network write first, fall back to local queue + local inventory deduction on failure, with a `revertOfflineVisit()` safeguard to prevent double-deducting stock when the same visit is edited and resubmitted multiple times while offline.

**Trigger points for synchronization** (where the app initiates these flows):
- App boot → `SplashScreen` → `AuthBloc.CheckAuthEvent` (no sync, just token check) → `DashboardScreen.initState` dispatches `LoadDashboardData` (pure local read) followed by `FetchDashboardData` (network fetch that internally calls `syncDown()` after caching server-derived dashboard stats into secure storage).
- Manual pull-to-refresh / refresh button on `dashboard_screen.dart` and `visit_list_screen.dart`.
- Every visit submission (`saveInvoice`) is itself a one-shot sync attempt, independent of the broader `syncDown`/`syncUp` cycle.
- Transfer response actions (`RespondToTransfer`/`RespondToBatchTransfer`) re-trigger `FetchDashboardData` (and hence `syncDown()`) after a successful PUT, to pull the now-updated inventory into the local cache.

**Persistence model**: SQLite (`wanasah_offline.db`, version 6 with incremental `onUpgrade` migrations) holds exactly three tables — `products` (flat vehicle stock snapshot), `visits` (flat visit snapshot with `cart_items`/`returns` as embedded JSON text, not normalized rows), and `pending_sync` (the offline write-ahead queue). This is intentionally a thin, denormalized cache rather than a mirror of the backend's relational schema — there is no local `shops`, `zones`, or `product_variants` table; everything the UI needs is embedded directly on the `visits`/`products` rows at sync time.

## 4. State Mutations & Side Effects

This section maps where a single business action causes state to change in more than one place (cross-module side effects), based strictly on the code paths already traced above.

- **`InventoryLedger` (per-session/day ledger)** is the append-only audit trail for everything that happens to a driver's `SessionInventory`: morning handshake (implicitly, via `SessionInventory` creation, no explicit ledger row at session start), sales (`update_visit`, type `'Sale'`), returns/exchanges (`'Exchange (Deduction)'`, `'Return (Addition)'`), reversals of edited visits (`services.reverse_previous_visit_state`, types `'Adjustment (Reversal)'`/`'Adjustment (Reversal Return)'`), mid-day transfers (`'تأكيد استلام حمولة'`/`'تأكيد سحب حمولة'`/`'Batch Accepted'`/`'Batch Rejected'`), and end-of-day settlement (`'Surplus'`/`'Deficit'`/`'END_DAY_CLEARANCE'`/`'VEHICLE_ROLLOVER'`/`'Warehouse Return'`). Every one of these mutation points independently re-implements the "lock → read expected → mutate → write ledger row" pattern rather than calling through `services.adjust_inventory()` uniformly (only `api/driver.py`'s reversal path uses the shared service; `dispatch.py` inlines its own logic) — this is the same duplication risk already flagged structurally in `01_ARCHITECTURE.md` §6, now confirmed from the data-flow perspective: **the same conceptual state transition (inventory adjustment + ledger write) has at least three independently-maintained implementations** (`services.adjust_inventory`, the inline logic in `api/dispatch.py`, and the inline logic in `api/warehouse.py`).
- **`WarehouseLedger` (central warehouse ledger)** mirrors every movement of stock into/out of `MainWarehouse.available_quantity_packs`/`reserved_quantity_packs`: supplier inbound (`INBOUND_SUPPLIER`), stocktake corrections (`AUDIT_ADJUSTMENT`), morning dispatch load/unload (`DISPATCH_LOAD`/`DISPATCH_UNLOAD`), mid-day handshake reserve/commit/release (`HANDSHAKE_RESERVE`/`HANDSHAKE_COMMIT`/`HANDSHAKE_COMMIT_PULL`/`HANDSHAKE_RELEASE`), settlement returns (`DISPATCH_UNLOAD`/`DISPATCH_UNLOAD_FALLBACK`), and manual ledger corrections (`INBOUND_CORRECTION`). This ledger is the only place all three "physical location" states of stock — warehouse shelf, vehicle, driver's live custody — are reconciled against each other, and it is computed at read-time in `GET /warehouse/inventory` via five parallel subqueries (damaged, sleeping vehicles, active session inventory, pending pulls) joined against `ProductVariant`/`MainWarehouse` — a single request that aggregates state scattered across five tables into one denormalized view for the React dashboard.
- **`Shop.current_balance` (debt ledger)** is mutated in exactly two request paths: `update_visit` (new debt added / debt collected during a visit) and `services.reverse_previous_visit_state` (undoing a previous visit's financial effect when the same visit is edited again). Both paths enforce `current_balance >= 0` at the application level before commit (raising `400`/`InventoryReversalError` rather than letting the DB `CheckConstraint` fail with a raw 500), and both write a `SystemAuditLog` row (`DEBT_COLLECTION` / `CASH_REVERSAL_ALERT`) as a side effect when money changes hands — meaning every debt mutation has a guaranteed, queryable audit trail independent of the `Visit` row itself.
- **`SessionInventory` (driver's live custody)** is the most frequently mutated table in the system per unit of time: it changes on session start (bulk creation from `VehicleLoad`), every accepted mid-day transfer, every sale/return/reversal inside `update_visit`, and the final settlement pass. It is also the table read most differently by different consumers: the driver's own dashboard (`GET /driver/{id}/dashboard`) reads it directly for "what's left in my van", while the admin's live dashboard (`GET /admin/sessions/today`) reads the *same* rows to compute `sold_quantity = starting+net_transfers-remaining` for the fleet radar — i.e., one write produces two independently-computed read projections for two different UIs.
- **`DamagedItemLog`** is populated only at settlement time (`settle_session`), by re-reading `VisitReturn` rows tagged `Expired`/`Damaged`/`Factory_Defect` that were created hours earlier during individual visits — meaning damaged-goods accounting is deliberately deferred and batched to end-of-day rather than being written immediately when the return happens in the field.
- **`SystemAuditLog`** is the catch-all cross-cutting side-channel: authentication brute-force tracking, settlement cash/inventory discrepancies, debt collection, cash reversal warnings, and unauthorized ledger-adjustment attempts (wrong password on `POST /warehouse/ledger/{id}/adjust`) all write to this same table with a free-text `action_type` — it functions as an implicit event log consumed only by direct DB inspection; there is no dashboard UI in the reviewed React codebase that surfaces `SystemAuditLog` contents back to an admin.
- **Local (Flutter-side) state mutation mirrors**: every server-side inventory mutation described above has a **client-side shadow mutation** for immediate UI feedback: `deductInventoryLocal()` mirrors a sale's effect on `products.current_cartons/current_packs` the instant `saveInvoice()` is called (online or offline), and `revertOfflineVisit()` mirrors a reversal. These local mutations are **not** transactionally tied to the server's actual outcome when the network call succeeds "immediately" — the local deduction always happens in parallel with (not strictly after confirmation of) the authoritative server-side ledger writes, relying on the next `syncDown()`'s full `refreshSessionData()` overwrite to correct any drift.

## 5. Data Flow Bottlenecks & Weak Points

- **Client-side polling instead of push updates.** `OperationsDashboard.tsx` polls `GET /admin/sessions/today` every 10 seconds via a recursive `setTimeout`, and `DispatchBoard.tsx` polls `/dispatch/active_routes` + `/dispatch/shortages` every 60 seconds via `setInterval`. Both are full-payload re-fetches (not deltas) with no ETag/If-Modified-Since or WebSocket alternative — as fleet size grows, this is a linearly-scaling load on the same `AsyncSession`/connection pool that also serves every driver-facing write, and the 10-second cadence means the admin's view of "who is doing what right now" is inherently up to ~10 seconds stale, which is explicitly acknowledged in the code (`// سيتم تعديله عند بناء WebSockets`).
- **Driver-side pending-transfer polling is fetch-on-demand, not push, either.** `CheckPendingTransfers` is only dispatched after a successful `FetchDashboardData`, meaning a driver only discovers a new mid-day inventory transfer when the dashboard happens to refresh (manual pull or app resume) — there is no periodic background poll or push channel for this, so a transfer created by dispatch can sit unseen by the driver for an arbitrary length of time if they don't manually refresh.
- **`update_visit` is a single, very large, multi-concern transaction.** One HTTP request can: reverse a previous visit's entire financial/inventory state, validate zone/shortage/emergency rules, run a same-day sample-quota aggregation query, process N cart items and M returns each requiring an `OfferRule` scan and inventory lock, mutate `Shop.current_balance`, and conditionally delete duplicate pending visits — all inside one DB transaction with several sequential `with_for_update()` locks (`Visit`, `Shop`, `SessionInventory`). Under concurrent load (e.g., two visits for the same shop submitted near-simultaneously, or a settlement running for the same session), this creates a long lock-hold window that increases the chance of lock contention/timeouts compared to smaller, more granular transactions.
- **Duplicated inventory-mutation logic increases risk of silent data-flow divergence.** As noted in Section 4, the same conceptual operation (deduct/add packs + write a ledger row) is implemented independently in `services.adjust_inventory()`, inline in `api/dispatch.py` (dispatch/handshake/settlement), and inline in `api/warehouse.py` (inbound/stocktake/ledger adjustment). Because these are separate code paths reading and writing the same tables (`SessionInventory`, `MainWarehouse`, `InventoryLedger`, `WarehouseLedger`), any future change to accounting rules (e.g., how partial packs are rounded, or what counts toward the daily sample cap) must be manually replicated in multiple places — a single missed update would cause the three "views" of inventory (session, vehicle, warehouse) to drift out of sync from each other without any automated cross-check.
- **Offline visit data loss window on true "poison pill" JSON.** `_dispatchPendingRecord`'s `default:` branch silently logs and skips any `pending_sync` record with an unrecognized `type` — this is a deliberate defensive choice (per the code's own comments) to avoid freezing the whole queue, but it also means a pending record that can never be dispatched (e.g., a corrupted/legacy `type` value) will remain in `pending_sync` forever with no user-facing surfacing of that fact — the driver has no UI indicator listing exactly which pending items are permanently stuck versus normally queued.
- **`revertOfflineVisit()` only reverses cart-item quantities, not returns.** The comment in `SyncRepository.saveInvoice()` explicitly states returns are intentionally left untouched during an offline resubmission revert ("المرتجعات نتركها للسيرفر لتجنب العبث بالعهدة") — meaning if a driver edits an already-queued offline sale that also included returns, the local vehicle-stock view for returned/damaged items can diverge from the eventual server-computed truth until the next full `syncDown()` overwrite.
- **No optimistic-concurrency/version check between `settle_session` and a late-arriving offline sync.** `settle_session` locks `SessionInventory` and finalizes `is_settled=True`, but a driver's device that is still offline at that moment (with visits already recorded locally and queued in `pending_sync`) has no way to know the session was just settled until its own `syncUp()` attempt gets a 4xx from `update_visit`'s `is_settled` guard — at which point (per the "keep it in queue for manual fix" logic in `syncUp()`) that visit remains permanently stuck in the offline queue, since the business rule (403, settled session) will never resolve itself and there is no explicit UI flow shown in the reviewed screens for a driver to discard/acknowledge a permanently-rejected queued item.
- **Hardcoded/divergent network configuration on the React side.** `pages/Login.tsx` calls a hardcoded `http://127.0.0.1:5000/login` instead of going through the `VITE_API_URL`-driven `useAuthFetch()` used everywhere else — in any environment other than local development this is a dead code path that would silently fail to reach the real backend, representing a data-flow break at the very first step of the admin's session (distinct from, but related to, the token-storage fragmentation already noted in `01_ARCHITECTURE.md`).
- **React has no compile-time response contract.** Because dashboard fetches are typed as `any`/loosely-typed JSON (no shared schema/DTO layer mirroring the backend's Pydantic models), a backend field rename or type change (e.g., a monetary field changing from string to number) would only be caught at runtime in the browser, not at build time — this is a structural weak point specifically in the *data flow validation* sense, distinct from the general "no data layer" architectural weakness already noted in `01_ARCHITECTURE.md`.
